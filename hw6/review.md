# Ревью report.py

## Найденные проблемы

| # | Функция | Что не так | Сценарий (вход → неправильный результат) | Серьёзность |
|---|---------|-----------|------------------------------------------|-------------|
| 1 | `read_orders` | Возвращает генераторное выражение, которое читает `f`, но `with` закрывает файл в момент `return`, до того как генератор потребят. | `list(read_orders('orders.txt'))` → `ValueError: I/O operation on closed file`. | падение |
| 2 | `build_report` | `orders` — одноразовый генератор, он потребляется в `count = sum(1 for _ in orders)`, а потом снова передаётся в `totals_by_user` и `has_large_orders`, где уже исчерпан. | Отчёт по `orders.txt`: `totals == {}`, крупные заказы считаются по пустому потоку. Реальные суммы теряются молча. | тихо неверный |
| 3 | `totals_by_user` | `groupby` группирует только ПОДРЯД идущие строки. Файл не отсортирован по пользователю, поэтому один user разбивается на несколько групп, и последняя перезаписывает предыдущие. | `[anna,100],[bob,50],[anna,700],[kate,300],[bob,30]` → `{'anna':700.0,'bob':30.0,'kate':300.0}` вместо `{'anna':800.0,'bob':80.0,'kate':300.0}`. | тихо неверный |
| 4 | `has_large_orders` | `return bool(large)` — объект-генератор всегда истинный, содержимое не проверяется. | `has_large_orders([['anna','100'],['bob','50']], 1000)` → `True`, хотя крупных заказов нет. | тихо неверный |
| 5 | `vip_over_limit` | `zip(vip_users, vip_limits)` молча обрезает по более короткому списку, а привязка к двум параллельным спискам хрупкая: при рассинхроне или коротком `vip_limits` VIP, которого надо проверять, тихо выпадает из проверки без ошибки. | На данных задания результат совпадает с верным (`['anna','bob']`), потому что выпадает именно Кейт, которую по решению и надо пропустить. Но если задумано `vip_limits=[500,10,200]` (у Кейт лимит 200), а по ошибке передали `[500,10]`, то Кейт с тратой 300 превышает свой лимит, а результат молча остаётся `['anna','bob']` вместо `['anna','bob','kate']`. | тихо неверный (латентный) |
| 6 | `last_orders` | `f.readlines()` загружает весь файл в память ради последних `n` строк. | На многогигабайтном `orders.txt` процесс съедает память/падает по OOM; результат при этом правильный. | производительность |

Примечание к проблеме 5. В отличие от остальных, она латентна: на данных задания прямой вызов
`vip_over_limit` даёт одинаковый результат в обеих версиях (усечение `zip` выбрасывает ровно Кейт,
которую и надо пропустить), поэтому отдельным unit-тестом она не изолируется. Её регрессия ловится на
уровне `build_report` (где `report.py` падает по проблеме 1), а прямой вызов в `test_vip_over_limit`
лишь фиксирует согласованное решение по Кейт. Это улучшение надёжности (явный проход по `vip_users`
вместо молчаливого усечения), а не исправление неверного результата на валидных данных.

## Как исправлено (report_fixed.py)

1. `read_orders` переписана как генераторная функция с `yield` внутри `with` — файл закрывается только когда генератор исчерпан или закрыт.
2. `build_report` открывает `read_orders(path)` заново для каждого потребителя (count, totals, has_large); память остаётся O(1).
3. `totals_by_user` накапливает суммы в словаре за один проход, порядок строк не важен.
4. `has_large_orders` использует `any(...)` — реально смотрит значения и останавливается на первом крупном заказе.
5. `vip_over_limit` строит `dict(zip(...))` и проходит по `vip_users` с явной проверкой наличия лимита.
6. `last_orders` использует `collections.deque(maxlen=n)` — в памяти только последние `n` строк.

## Решение по Кейт (VIP без лимита)

Кейт перечислена как VIP, но лимит для неё не задан. Выбранное поведение: **VIP без явного
лимита считается немониторимым и пропускается** (не попадает в список превысивших). Обоснование:
«лимит не задан» — это «порог не настроен», а не «порог равен нулю»; трактовать отсутствие порога
как нарушение (всегда флажить) значило бы поднимать ложные тревоги на любой трате. Падать с ошибкой
тоже нельзя — один непрописанный лимит не должен ронять весь отчёт. Поэтому ожидаемый результат на
тестовых данных — `['anna', 'bob']`, Кейт в него не входит. Отличие от оригинала в том, что здесь
пропуск сделан ЯВНО (проход по `vip_users` + проверка `u in limits`), а не как молчаливый побочный
эффект усечения `zip`.

## Правильный отчёт на тестовых данных

```
orders: 5
totals: {'anna': 800.0, 'bob': 80.0, 'kate': 300.0}
has_large: False
vip_over_limit: ['anna', 'bob']
last: ['anna,700', 'kate,300', 'bob,30']
```
